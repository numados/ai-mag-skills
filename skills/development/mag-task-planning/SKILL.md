# Task planning

Turn the understood problem and supported solution direction into a plan that someone can execute and verify, without implementing it. Research explains what problem to solve and which direction fits; planning chooses how best to realize it within the actual system and constraints. A research recommendation is an input to validate, not an approved design or permission to expand scope. Planning does not authorize product-file changes or tracker updates. Memory-record writes are allowed only through the optional integration below or an otherwise authorized handoff destination; they do not permit other remote mutations. Reply in chat by default; persist the plan only when requested or permitted by the surrounding workflow. A request for a plan does not authorize implementation.

## Optional memory

If `mag-task-storage` is available in the harness skill catalog or explicitly supplied, read and apply it to restore the task's relevant research, decisions and useful knowledge, then preserve the plan and its actual approval status within its destination and permission rules. Missing stored research does not require a separate research stage. Without the storage skill, keep the existing chat-default behavior and optional handoff; do not require storage or invent a replacement protocol.

## Establish the task and evidence

- Identify the desired outcome, authorized scope, constraints and supplied sources. A written task is enough to start; a research handoff is optional. Distinguish requirements and user decisions from observed facts, proposals and assumptions. Repository conventions inform implementation but do not authorize new product behavior.
- Resolve a tracker URL or ID with suitable available read-only capabilities, without assuming a provider or access. If an ID is ambiguous, ask which source it identifies. If a decision-relevant source is inaccessible, report the gap and request the smallest useful excerpt or clarification. Do not install tools, authenticate or change state without authorization.
- Inspect relevant current repository instructions, code, contracts, configuration, tests and consumers as needed. When current source is accessible, inspect it instead of assuming an older excerpt or handoff still applies. When it is unavailable, distinguish supplied excerpts from verified current behavior and give a useful preliminary plan where possible. Before implementation, verify the actual source; if it differs materially, stop and revise the affected plan before proceeding. Cite useful paths or source references, and distinguish an unsuccessful search from proof that something does not exist.

## Design the implementation

- Discover and apply suitable skills exposed in the current harness or explicitly supplied for consequential design choices. Use design/construction, language/framework, integration or testing skills where they improve this plan; for example, `mag-code-design` for internal structure and `mag-code-construction` for project fit and technology verification when available. Read the relevant guidance rather than merely naming a skill for later execution. Apply it under this request's plan-only and permission boundaries, even if the skill also supports implementation. Do not require a particular skill, install missing resources or claim unavailable capabilities; use accessible evidence and disclose material limits instead.
- Start with the simplest fitting approach and existing conventions. Compare alternatives when a consequential trade-off warrants it, then justify the preferred approach against the actual requirements, compatibility, complexity and testability; there is no universally best architecture. Specify the necessary responsibilities, component and interface boundaries, dependency direction, data flow and relevant failure/lifetime behavior. Give each changed rule or mapping one owner. Identify concrete existing paths and symbols, and clearly label proposed new ones, so the implementer need not rediscover placement and integration. Scale this design to the change rather than adding layers or full code listings by default.
- Preserve the existing architecture by default at the system integration boundaries, but do not confuse preservation with copying poor local code. For new functionality, plan new files, modules, classes or focused abstractions when they give the change a clean, cohesive design; choose their ownership, contracts and dependency direction deliberately. In an existing repository, connect new components through the current composition, dependency-registration, configuration, public-contract and lifecycle boundaries, and trace callers, consumers and tests. In a new repository, design the architecture appropriate to the approved requirements rather than preserving a nonexistent legacy shape. For corrections, keep improvements focused on the changed behavior and surrounding code needed for a safe integration; do not expand into unrelated legacy refactoring. Do not rename or move existing layers, replace system-wide patterns, change established public contracts, or redesign existing dependency direction merely because another shape looks cleaner. A system-wide architectural redesign is a separate scope decision: require an explicit user/owner request or approved requirement for it. If the requested behavior cannot be integrated safely within the current architecture, show the concrete evidence and stop with a focused decision about redesign; do not smuggle a redesign into ordinary implementation phases.
- Resolve technology details that can change the design before treating it as executable. Establish the applicable language, runtime, framework, library and provider versions from project evidence. For unfamiliar or version-sensitive behavior, use suitable available documentation capabilities and authoritative version-applicable sources, including official documentation when permitted; inspect exact APIs, constraints and compatibility needed by the proposed code. Reuse verified evidence while current, not model recollection or a newer-version example as proof. Record consequential findings and sources in the plan. If confirmation is unavailable, disclose the uncertainty and block only dependent choices or steps; do not invent an API, upgrade a dependency or prescribe a fallback to fill the gap.

## Shape the plan

- Map each requirement to the existing integration points and intended change, including the extension point, callers, registrations, configuration, contracts, tests and downstream consumers affected by added or corrected code. For new files or modules, state their responsibility, ownership, public/internal boundary and connection to the existing system. Describe coherent, appropriately sized steps and dependencies; avoid speculative layers, system-wide architecture rewrites or unrelated cleanup.
- Do not silently add scope-bearing behavior such as a public interface, persistence, infrastructure or new failure semantics. Label implementation choices as proposals and explain material trade-offs; established facts do not grant product scope. Even a conditional scenario needs evidence or approval for its expected outcome; do not invent failure or recovery rules. Seek authorization when a choice changes scope or requires a product decision.
- Investigate decision-relevant unknowns before asking. If evidence cannot resolve a consequential choice, state its impact and ask the smallest specific question that unlocks the next decision; avoid a speculative checklist of possible future requirements. For each step that could expose behavior affected by that decision, explicitly mark the step blocked and name the decision or evidence that unblocks it; do not list it as an independently executable change or treat an unverified option as settled. Technical separability alone does not establish safety. Before reporting, check the dependency labels: if a step depends on a blocked decision, that step must also be blocked, even if presented as a draft or proposal. Check acceptance criteria and tests for conflicting expected outcomes. Continue planning genuinely independent work and label non-blocking uncertainties without delaying the whole plan.
- Define observable acceptance criteria and executable, focused checks that exercise the actual behavior and integration, including relevant failure and compatibility cases. Identify existing tests or commands when verified; otherwise describe a concrete test and disclose that its command or environment needs confirmation. Do not claim checks have run when they have not.

## Report

Right-size the response to the task: state the outcome and scope, relevant evidence, the chosen design and why it fits, current and intended integration, ordered steps, acceptance criteria and verification, and material risks or open decisions. Separate authorized requirements from proposed choices and note inaccessible sources and unverified assumptions. For a small change, a compact list may be sufficient; for a blocked decision, provide the useful partial plan and focused question rather than false precision.

When the user or surrounding workflow expects task tracking, prepare a plan handoff with task identity, scope and approval status, evidence, chosen design and rationale, relevant technology constraints, phases and dependencies, checks, open decisions and next action. Use the optional memory integration when available; otherwise save locally only when the destination and write are authorized, or provide it in chat. Do not invent a destination; a remote memory write requires the integration's explicit permission boundary and does not authorize tracker or other remote changes. If persistence is expected but no suitable destination is known, ask; report any failed write. A saved plan does not authorize implementation.
