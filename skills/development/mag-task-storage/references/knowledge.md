# Reusable knowledge

Knowledge is a maintained explanation, contract, constraint, decision or verified practice that remains useful beyond one task. A task-specific plan, event, temporary hypothesis or search transcript stays in the task record unless a reusable conclusion is deliberately selected.

## Read

Search the resolved knowledge section with bounded terms and scope. Read only the best candidates and needed sections; follow source or task links when they can change the answer. Cite the record and the underlying evidence where useful. Distinguish a recorded rule from a verified current implementation. A missing search hit does not prove no relevant knowledge exists.

Knowledge lookup needs no task record. Do not create a task or event merely to answer a read-only knowledge question.

## Create, update or promote

Require authorization to change knowledge, independently of permission to log task progress. For a requested promotion from task work:

1. Select the reusable claim and its intended audience/scope; leave the full work history in the task.
2. Check supporting sources, applicability, revision/version and meaningful contradictions. Keep unresolved assumptions explicit rather than making them established policy.
3. Search for an existing note before creating one. Update the appropriate note or link related material instead of producing duplicate truth.
4. Prepare generic Markdown using the bundled [Obsidian note format](obsidian-note-format.md). Use the provider's knowledge operation when available; hand off supported metadata and content so it can choose placement. Otherwise maintain the note through compatible authorized record tools/files, optionally guided by a discovered writer skill. Preserve established schema and links; report any required metadata that cannot be mapped before writing.
5. Verify the resulting note and rediscovery. Link the originating task or source when useful without copying private conversations or secrets.

For a new generic Markdown knowledge note, combine the shared envelope with the useful explanation, applicability, evidence/provenance and material uncertainty or replacement relationship. If `mag-knowledge-capture` is available, let it own knowledge kinds and reconciliation; do not invent a second taxonomy. Without it, a generic note needs no kind taxonomy. Follow neighboring metadata conventions rather than imposing a new schema. Explicitly requested proposals may be stored as proposals, not facts.

When correcting knowledge, explain the evidence and preserve useful provenance. Use an established supersede/retire mechanism for obsolete notes rather than silently deleting them. Knowledge maintenance does not alter historical task events or approve a new feature. Do not automatically promote every completed task or infer permission from completion.
