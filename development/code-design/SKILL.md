# Code design

Design for the behavior and constraints at hand, not for a pattern name. Respect the requested scope: a design discussion does not authorize code changes.

1. **Frame the problem.** Identify the requested outcomes, current pain, relevant constraints and observable behavior. Inspect the smallest relevant portion of the project, including callers, existing contracts, language idioms and tests; reuse verified context while current. Distinguish requested behavior and observed facts from assumptions and proposals. Keep unverified assumptions explicitly conditional throughout the design; do not treat them as established facts in the recommendation or walkthrough. Do not add a mechanism, workflow or externally observable behavior merely because it might be useful: present it as a proposal when it requires an unrequested decision. Ask a focused question if an unresolved requirement would materially change the design.
2. **Shape responsibilities and contracts.** Decide which decisions and data belong together and where dependencies should point. For each meaningful interface, consider caller needs, inputs and outputs, invariants, ownership and lifetime, failures and side effects, and compatibility where relevant. Hide decisions callers do not need to know; do not split a responsibility merely to create another layer.
3. **Compare fitting options.** Start with a direct solution using existing project conventions. Consider alternatives only when they address an actual need or a consequential trade-off. Weigh clarity, coupling, complexity, testability and cost of change against the requested behavior. Consider language features and existing abstractions before introducing new types or indirection.
4. **Use patterns selectively.** A named pattern is a candidate, not a requirement. Identify the problem it solves, why it fits this context, its participants and collaboration, and its costs compared with the simpler alternative. If no pattern helps, say so and keep the direct solution. For a pattern choice or comparison, read [pattern selection](references/patterns.md); do not load the reference for unrelated design work.
5. **Check the design.** Walk through a representative success and relevant failure or edge case across the proposed interfaces. For an external operation, distinguish a definite failure from an unknown outcome: an effect may have happened even if its response was lost. Do not assume a retry is safe or that the existing contract supports a new outcome; verify the contract and applicable idempotency or recovery guarantees. If the contract cannot represent the outcome, do not prescribe returning or surfacing a new state or error as though it already exists. Mark the affected path as unresolved, identify the compatibility gap, and ask for the decision needed before proposing a change; keep the summary and walkthrough consistent with that limitation. Check that responsibilities, invariants and dependency direction remain coherent; consider how behavior can be tested through a useful boundary. Identify compatibility implications and unresolved assumptions without inventing requirements or claiming tests ran.
6. **Communicate proportionately.** Explain the proposed structure and interactions, the reason for consequential choices, relevant trade-offs, and open questions. Include only detail needed for the decision. For implementation, work within the user's authorization and verify actual changes; use suitable available construction, testing or refactoring skills when relevant, otherwise proceed with your own knowledge without claiming to have used an unavailable skill.
